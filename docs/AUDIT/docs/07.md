### Phase 7. Security controls and policy enforcement

Purpose: security denials should be correlated to services and desktop.

* AppArmor denials (group by profile and target)
* SELinux (if present)
* Kernel lockdown / secure boot interactions (optional)

## Mandatory access control and policy denials

* **SELinux AVC denials** (if enabled)

  * Symptoms: `avc: denied`, `SELinux is preventing ...`
  * Sources: auditd logs, journal, `/var/log/audit/audit.log`
* **AppArmor denials** (you already have)

  * `DENIED`, `apparmor="DENIED"`
* **Landlock** (newer, per-process sandboxing)

  * Less common, but can block filesystem actions depending on apps.

## Kernel level protections that look like denials

* **seccomp** (syscall filters)

  * Symptoms: `seccomp` / `SECCOMP` / `Operation not permitted` with audit lines
  * Often from browsers, sandboxed apps, containers, hardened services.
* **kernel lockdown mode** (often when Secure Boot is on)

  * Blocks: kexec, /dev/mem, some MSR access, some debug interfaces.
  * Symptoms: “Lockdown:” messages.
* **LSM stacking interactions**

  * Multiple LSMs (AppArmor + Yama + Lockdown + BPF LSM) can produce confusing “EPERM”.

## Audit and auth controls (not “denials” but enforcement points)

* **auditd / audit rules**

  * Can look like “denied” events if you only grep for failure codes.
  * What matters: `res=failed`, `exit=-EPERM` / `-EACCES`.
* **PAM / polkit**

  * polkit blocks privileged actions in GUI apps.
  * Symptoms: `polkit` messages, auth agent prompts failing, “not authorized”.
* **sudoers and group membership**

  * Not a “denial log” category, but it causes consistent EPERM patterns.

## Filesystem policy and mount based denials

* **Mount flags**: `noexec`, `nodev`, `nosuid`, `ro`

  * Breaks app launch, helpers, installers, games, some desktop portals.
* **Permissions and ACLs**

  * Classic `EACCES`, but still a real security boundary.
* **Extended attributes / IMA / EVM**

  * Integrity enforcement can block execution if configured.
* **fscrypt / LUKS state**

  * Missing unlock can look like permission errors.

## Firewall and network policy

UFW rules are not typically “denials” in the same sense as AppArmor, but they are security enforcement and can break services.

* **UFW / iptables / nftables**

  * “Denied” shows up as dropped packets, not process denials.
  * Evidence:

    * UFW logging if enabled: kernel log lines with `UFW BLOCK`.
    * nftables counters/trace if configured.
* **NetworkManager “firewall zone”**, **firewalld** (if used instead of UFW)

  * Can apply zones and policies dynamically.
* **DNS policy**

  * systemd-resolved DNSSEC failures, split DNS, captive portals.
  * Looks like “network broken”, not “denied”, but still a control plane issue.

## Container and sandbox layers

* **Flatpak permissions**

  * Denials are frequent and expected.
  * Evidence: `flatpak info --show-permissions`, portal failures in journal.
* **Snap confinement**

  * AppArmor-backed denials tied to snap profiles.
* **systemd sandboxing**

  * Hardening knobs: `ProtectSystem=`, `ProtectHome=`, `NoNewPrivileges=`, `RestrictAddressFamilies=`, `SystemCallFilter=`
  * These produce EPERM and can look like AppArmor issues.

## Device and bus access controls

* **udev rules**

  * Device node permissions, group ownership.
* **logind seat/session access**

  * Can block device access from user sessions (common with input devices, backlight, some GPU nodes).
* **DBus policy**

  * Blocks method calls. Shows as “Rejected send message” or similar.

## Practical “security factors” that masquerade as denials

* **Clock / time sync issues**

  * Break TLS, login flows, package repos.
* **Broken CA trust store**

  * Looks like “can’t connect”, effectively blocks.
* **Crypto policy**

  * FIPS mode or disabled algorithms can break apps quietly.

## What to include in your audit (minimal, high-signal)

Add these checks as separate subsections under "Security controls":

1. **LSM status and denials**

* AppArmor, SELinux, Lockdown, Yama, seccomp hits.

2. **Privilege mediation**

* polkit failures, sudo failures.

3. **Sandbox layers**

* Flatpak portal failures, Snap denials, systemd unit sandboxing violations.

4. **Network enforcement**

* UFW blocks (only if logging enabled), nftables ruleset summary and counters.

5. **Mount and filesystem policy**

* `noexec/nosuid/ro` mounts, home encryption locked state.

If you want this to be actionable, don't just count events. For each bucket: group by `(subject, target, operation, profile/rule)` and output top offenders.
